### The bug

`mvpe_rel_l2_per_sample` pools all 36 probes into **one** relative L2. The real kit takes a
relative L2 **per probe column** — each of the 4 x-stations normalized by its own 9-site × 2-channel
target norm — then averages the four. Per-column denominators up-weight the far wake where
velocities are small, so the pooled form is **systematically pessimistic by 10–14 %**.

The per-column form is not a guess. It reproduces both anchors to four decimals, and it is
transcribed independently three times in this repo from when the kit was still reachable:

* `unet/train2.py:407-420` — commented *"scoring.mvpe_rel_l2_per_sample, **verbatim**"*
* `diag_mean_floor.py:36-43` — *"scoring.mvpe_rel_l2 on already-time-averaged fields"*
* `diag_history.py:71-73`

Rejected alternatives (all in the script's diagnostic section): per-ROW (0.3056 / 0.2925),
pooled-36 across samples (0.1345 / 0.1097), per-point mean relative error (diverges). TKE
`ddof` is **not** discriminable from these anchors — both predictors are constant in time, so
`var_t(P)=0` and TKE = 1 for either convention; `ddof=0` is retained as the numpy default.

### Fix — NOT APPLIED

Editing the reconstruction was blocked by policy (another agent owns code changes), so it is
handed over rather than committed. In
`~/RealPDE/realpde_t1_starting_kit_v9/realpde_t1_starting_kit_v9/scoring.py`:

```python
def _probe_means(A, mc: int = 2):
    a = np.asarray(A, np.float64)[..., :mc].mean(axis=1)
    a = a[:, PROBE_Y[:, None], PROBE_X[None, :], :]                    # (N, 9, 4, mc)
    return a.transpose(0, 2, 1, 3).reshape(len(A), len(PROBE_X), -1)   # (N, 4, 9*mc)

def mvpe_rel_l2_per_sample(P, Y):
    p, t = _probe_means(P), _probe_means(Y)
    per_col = np.linalg.norm(p - t, axis=2) / np.linalg.norm(t, axis=2).clip(1e-8)
    return per_col.mean(axis=1)
```

`mvpe_rel_l2` (mean over samples) is unchanged. The `.clip(1e-8)` is a no-op on this data
(minimum column target norm 0.102) and only guards a degenerate column.

**Blast radius: all 24 call sites**, because everything reaches MVPE through these two
functions — and that includes **SPS**, whose per-sample accuracy factor weights mvpe at 0.2. So
`mvpe_score` *and* `sps_score` are both wrong until this lands, in the pessimistic direction.

### Interim workaround — `Track_1/mvpe_fix_20260829.py`

Rebinds the function at runtime on every live copy of the kit module and wraps any entry point:

```
python mvpe_fix_20260829.py compare_v9 --ckpt unet/fno_vl_s1.pth --aoa 15 20
python mvpe_fix_20260829.py selftest     # re-checks both anchors
```

It patches **both** kit instances: `sps9` and `eval_v9` each build their own with
`importlib.util.module_from_spec` and neither registers in `sys.modules`, so patching one leaves
the other stale. `compare_v9` scores through `sps9.sc`; `eval_v9`/`ens_v9` score through
`eval_v9.sc`. Delete this file once `scoring.py` is fixed.

## 5. The binding resource is 12 CPU cores, not the GPU

**GPU utilization sat at 0 %, 765 MHz, 47 W for the entire run** — including the fast epochs.
That is not idleness; it is a 0.91M model on a 32×64 grid issuing many tiny kernels, which
nvidia-smi's sampler does not register. *Do not use `nvidia-smi` utilization to judge whether
this workload is running.* The honest split, measured:

| per batch (of 377/epoch) | ms | s/epoch |
|---|---|---|
| `fetch()` — 64 CPU tensor slices + `stack` + H2D | 8.85 | 3.3 |
| model fwd + bwd + AdamW | 8.52 | 3.2 |
| losses, normalization, accounting | ~0.5 | ~0.3 |
| **total** | **~17.9** | **~6.8** ✓ |

So the step is ~50 % CPU-side data assembly, and the whole loop is dispatch-bound. Consequences:

* **Slurm gives this job 12 cores (cpuset 112–123) out of 128.** Three separate CPU-heavy jobs
  landed on those cores during the run — a sibling agent's scripts, and (twice) my own numpy
  validation scripts, which chew several cores for ~60 s on the 201 MB `val_*.npz` files. Each
  collision cost a 4–10× slowdown while it lasted.
* `OMP_NUM_THREADS` is **not** the lever: 12 / 4 / 1 threads give 8.52 / 8.61 / 9.08 ms per step.
* **Operational rule for the campaign: serialize CPU-heavy work against training.** The GPU is
  not the contended resource and "one training at a time" is not a sufficient rule — a plain
  numpy eval script is enough to halve training throughput. If two agents must work at once,
  partition the cpuset with `taskset` (e.g. training on 112–119, everything else on 120–123)
  rather than relying on the scheduler.

## 7. Handover — items for the code owner

1. **`scoring.py` MVPE** (§3). Highest priority: every subscore table produced before it lands
   understates `mvpe` and `sps`.
2. **`_fno.load()` ignores `fgn_dim`.** `train2.py:571` *stores* `fgn_dim` in the checkpoint, but
   `submit_fno/_fno.py:278-291` never reads it, so `FNO2d` is built with `fgn_dim=0` and no
   `film` module. A checkpoint trained with `--fgn` will fail `load_state_dict` on unexpected
   `film.*` keys — which blocks the **Phase-F FGN gate**, since `compare_v9`, `eval_v9`,
   `ens_v9` and the submission all load through this one function. One-line fix:
   `fgn_dim=blob.get("fgn_dim", 0)` in the `FNO2d(...)` call.
3. **Optional, ~2× on training throughput**: `train2.py:329-330` assembles every batch with a
   Python list-comprehension of 64 CPU tensor slices plus `torch.stack`, then copies H2D. That
   costs **8.85 ms/batch = 3.3 s/epoch**, about half the whole step. Holding the trajectory store
   on the GPU (1.10 GB of 40 GB) and gathering with advanced indexing costs **0.18 ms/batch — 50×
   less**, taking the epoch from ~7.0 s to ~3.7 s. Worth it only if the queue gets tight; it
   changes no numerics but it does touch the hot path.
