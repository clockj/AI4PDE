### Incident: `ph4` was lost to an HDF5 file-lock race, and the queue was re-planned around it

Slurm put **q2b and q2d on the same node (a0149)** and both opened the same `train_real` `.h5`
files in the same second. h5py's default advisory locking on this mount returns
`OSError: [Errno 5] ... unable to lock file`, and q2b's first arm died on it before training
started. **It is contention, not a recipe bug**: the very next arm in the same job, `ph4e100`,
read the identical files seconds later and reported `296 trajectory-phases (4 phase(s)) ->
48160 windows`, exactly 4× the control's 12040. Fix is `HDF5_USE_FILE_LOCKING=FALSE`, which is
safe because every open in this project is read-only; it is set in `q2e` and in the resubmitted
`q2c`. Slurm snapshots a batch script at **submit** time, so patching the file could not reach
the already-queued 7161179 — it had to be cancelled and resubmitted (it was still held on its
dependency, so nothing was lost).

Losing `ph4` inverted the queue's duration ordering — q2b became the **shortest** job, not the
longest — so the dependencies were re-planned to minimise makespan. Durations: q2a ≈ 8.5 h,
q2b ≈ 2.9, q2d ≈ 7.8, q2c ≈ 7.0, q2e ≈ 5.6. Giving each freed slot to the **longer** waiting
job (`q2c` after q2b, `q2e` after q2d) ends at ≈ 13.4 h against ≈ 14.8 h for the reverse
pairing, and never runs more than three of ours at once: `[0,2.9] a,b,d` → `[2.9,7.8] a,d,c` →
`[7.8,8.5] a,c,e` → `[8.5,…] c,e`.

`ph4` is re-run rather than dropped because it and `ph4e100` test **different** hypotheses:
`ph4e100` holds the optimizer-step count at the control's 150.4 k (100 ep × 1505 steps =
150.5 k) so any difference is the **data**, while `ph4` holds the epoch count so it measures
data **and** steps together.

### Q1a/Q1b verdict — **bet 1 is dead, and the batch-position story was backwards**

1. **NO FAST PATH IS FASTER, and on Track 2 every one of them is SLOWER.** At 4 members the
   whole spread across seven variants is 1.408–1.486 A100 ms, i.e. **±2.7 %** — the best
   variant beats fp32 by **0.3 %**. At 8 members fp16+TF32 wins **5.6 %** (2.251 → 2.124),
   worth **+0.013 `final`**, which is inside a board `time_score` draw (±1.7 points ≈ ±0.16).
   On Track 2, batch 1 under a CUDA graph, fp32 is the *fastest* variant on both member sets
   and autocast costs **9 %** (2.742 → 2.996).
   → **The package is not FLOP-bound.** Plan §3 bet 1 assumed the 1×1 convs are ~70 % of the
   FLOPs and that tensor cores would halve the compute part; the FLOPs are there, the time is
   not. Doubling the members costs **1.59×** the time, not 2×, which is what a partly
   launch/bandwidth-bound kernel looks like. **The capacity axis is not going to be unlocked
   by precision.** Do not re-open TF32/fp16/bf16 for latency.
2. **PADDING THE TAIL BATCH CHANGES NOTHING — the hypothesis is falsified.** `fp32` and
   `fp32 + pad` agree to 0.001 ms and their permutation deltas are *identical to three
   significant figures*, and `perm333` (a genuinely partial tail) is no worse than `perm336`
   (none). Whatever position dependence exists is not the last, smaller batch.
3. **TF32 IS *MORE* PERMUTATION-INVARIANT THAN FP32, not less — round 15b's reading is
   reversed at this operating point.** With TF32 on, both member sets are **bit-identical**
   under permutation (0.00e+00) on both window counts; with TF32 off they are 3.2e-06 /
   4.1e-06. TF32 also changes the field by only **5–7e-05 rel-L2** and leaves all four scored
   subscores identical to four decimals. So the round-15b comment block in `submission.py`
   ("TF32 tiles a GEMM across the BATCH axis…") is right that precision changes batch
   sensitivity and **wrong about the sign for this model** — it was measured on 8 windows
   including a U-FNO, whose 3×3 convolutions carried ~20× the effect. It cost nothing to keep
   TF32 off (it is 5 % slower here anyway), so nothing was lost, but the stated reason is not
   the measured one.
4. **fp16 and bf16 are DISQUALIFIED on batch-position dependence, not on accuracy.** Their
   fields are within 6e-04 / 3.5e-03 rel-L2 of fp32 and their subscores are unchanged (bf16
   moves rel-L2 by 0.0001 and sps by 0.02), but permuting the windows moves an element by
   **9.5e-03** (fp16) and **4.7e-02** (bf16) relative — 3–4 orders of magnitude past the 1e-5
   gate and past `validate_strict.py`'s own 1e-4 bound. Turning TF32 on *with* fp16 restores
   exact permutation invariance (0.00e+00) — the algorithm selection, not the mantissa, is
   what carries the dependence.
5. **The only shippable fast variant is fp16+TF32+pad**, and it is worth **+0.000 `final` at
   4 members** and **+0.013 at 8**. There is no latency A/B worth a slot.

### Q1g.2 — the hot path, read against the source

`Track_1/submit_fno/_fno.py:StackedFNO._spec` (the shipped path), per layer:

1. `torch.fft.rfft2(_fft_in(x))` on `(112, 384, 32, 64)` — 43 008 2-D transforms. One call per
   LAYER on the fused tensor, **not** one per member (the member axis is folded into channels),
   so the FFT count is already minimal. Input is contiguous and fp32; `_fft_in` is the identity
   here.
2. `out = torch.zeros(b, k, wid, h, 33, dtype=cfloat)` — **a 363 MB allocation and zero-fill
   every layer**, 2.9 GB/batch of pure write traffic, to hold a tensor that is 81.8 % zeros by
   construction. This is the single most obviously wasteful line in the forward.
3. Two `torch.einsum("bkixy,kioxy->bkoxy", ft[:, :, :, sl, :mx], wc)` — **complex** contractions
   whose FIRST operand is a strided slice of the 363 MB spectrum and whose second is a strided
   slice of a 6-D parameter. einsum must permute both into a `bmm` layout, so each call
   materialises copies before it can call cuBLAS, and the GEMM it finally issues is complex
   with batch = K·my·mx = 384 and shape 112×96×96 — small tiles, no tensor cores.
4. `out[:, :, :, sl, :mx] = ...` — two strided scatters into that 363 MB tensor.
5. `torch.fft.irfft2(out.reshape(...))` — the full inverse.
6. In `forward`: `h + gelu(norm(spec + point))` is **four** full passes over a 352 MB tensor
   (add, norm, gelu, add).

`predict_fno`'s host side at this size: `dst` is pre-zeroed once (good), the whole window is
uploaded contiguous and sliced on GPU (good), members are averaged on the GPU before the
transfer (good) — but `dst[i:i+batch, ..., :2] = (...).cpu().numpy()` is still a **pageable**
D2H of 36.7 MB followed by a **non-contiguous** host write of the same size, per batch, and the
band stage then touches four 165 MB host arrays.

### Q1g.3 — the two rewrites, implemented and verified on CPU (GPU timing pending)

Both are opt-in, off by default, and inert when off.

**(a) `RPDE_SPEC=bmm` — `StackedFNO._spec_bmm` + `_packed`.** The complex product
`(Ar + iAi)(Br + iBi)` is a REAL matmul against the 2×2 block `[[Br, Bi], [−Bi, Br]]` fed
`[Ar | Ai]`, because that returns `[ArBr − AiBi | ArBi + AiBr]` = `[Re, Im]`. Same arithmetic —
a complex multiply *is* four real multiplies — but it becomes ONE contiguous real `torch.bmm`
that cuBLAS can batch and that tensor cores can take, instead of two complex einsums over
strided slices. The `+ky` and `−ky` blocks are concatenated along the MODE axis, so the two
einsums become one call, and the packed weights are built once on first use and cached as a
**non-persistent** buffer (they are a repacking of `w1`/`w2` and must never enter the
`state_dict`). It falls back to the shipped path whenever `min(my, h//2) != my` — `w2`'s rows
run backwards in frequency, so a clamped `my` would have to be taken from the other end, and
guessing there is how round 11 moved the field by 1.26.

**(b) `RPDE_TAIL=jit` — `_res_gelu`.** `h + gelu(z)` as one `torch.jit.script`ed kernel; two
full passes over a 352 MB tensor become one. Scripted inside a `try`, because this file must
import in the evaluation container under all circumstances and an opt-in that is OFF must never
be why a submission fails to load. (`torch.compile` is not an option there — no compiler in the
runtime image; `jit.script` needs none.)

**Correctness, CPU, three architectures** (`w24/(8,12)/L4/K2`, the shipped
`w96/(8,12)/L8/K4`, and `w32/(12,20)/L2/K3` to exercise mode padding):

| arm | `_spec` max rel Δ | full forward max rel Δ | verdict |
|---|---|---|---|
| `RPDE_SPEC=bmm` | 2.4e-07 / **2.9e-07** / 2.4e-07 | 2.2e-07 / **3.8e-07** / 2.7e-07 | float32 reduction order only |
| `RPDE_TAIL=jit` | — | **0.00e+00** | **BIT-IDENTICAL** |

The bmm path is not bit-identical and cannot be: a complex einsum and a real 2×2-block matmul
accumulate in different orders. 3.8e-07 relative is ~3 float32 ulp and is 4 orders below the
1e-3 field-deviation gate and 30× below the 1e-5 permutation gate, but **it is a change to the
numbers, so it needs the same batch-position test every Q1b variant got before it can ship** —
that is in the queued job (`lat_fast17.py`), not assumed here.

| repair | ms/window saved | `final` |
|---|---|---|
| A — contiguous buffer + one numpy 3-channel assembly | **−0.005** | −0.001 |

| pinned + async D2H | +0.004 | +0.000 |

**THE PROPOSED REPAIR IS THE WRONG ONE, AND THE RIGHT ONE IS A ONE-LINER.** The strided write
is not slow because it is strided — it is slow because **numpy's strided assignment is
single-threaded**, which is precisely what round 11 found about the band stage and never
applied to the write next to it. Through `torch.copy_` the identical strided write runs
**24× faster** (1.4 → 33.3 GB/s) and needs no second buffer. Option A is a **wash**, because
the one-shot assembly is itself a strided write of the same bytes and gives back everything the
contiguous per-batch write saved (−0.005 ms/window, i.e. very slightly negative). Option C
works but is strictly worse than B while adding a 110 MB buffer.
→ **Pinned + asynchronous D2H is worth ~nothing here**: the transfer is 21 MB/batch and already
runs at 93.7 GB/s, i.e. 0.004 ms/window in total. There is nothing to overlap. That closes the
overlap idea on arithmetic rather than on a failed implementation.
→ **The band stage is still the second-largest host item at 0.213 ms/window** even after round
11's rewrite, and it moves 495 MB in 71 ms = 6.9 GB/s. It is already threaded; what is left is
that it materialises `lower` and `upper` as two full 165 MB arrays.
→ Caveat, stated plainly: these are **login-node** numbers on a shared 12-core box and the run
above was the third attempt (the first two gave 15.5 and 10.5 ms for the torch row). The
RATIOS are the finding; the absolute ms come from job 7161342 on the compute node.

**`RPDE_HOSTW=torch` is implemented and BIT-IDENTICAL** end-to-end on CPU (predict_fno over 37
windows at batch 16: `np.array_equal` True, sigma identical, the `p` channel still exactly
zero), because `torch.from_numpy` is a view and `copy_` between two same-shape float32 tensors
is an exact copy. It is the third axis of the queued job's variant sweep
(`einsum/eager/numpy`, `bmm/eager/numpy`, `einsum/jit/numpy`, `einsum/eager/torch`,
`bmm/jit/torch`). Combined arm vs shipped: **2.25e-07** relative, all of it the bmm path.
